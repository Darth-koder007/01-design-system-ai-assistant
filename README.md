# Design-System AI Assistant

A static-analysis tool for a React design system, with an LLM layer on top: it detects real violations (raw HTML that duplicates a component, deprecated props, hardcoded colors that duplicate a design token), explains each one in plain language grounded in the component's actual prop API, and — where the fix is mechanical — generates a type-checked codemod diff. Runs against [the design system in this portfolio](../00-design-system).

This is a generalization of static-analysis work I did at Delivery Hero: a metrics dashboard that used the TypeScript compiler API to track design-system component usage across repositories. That project answered "how much is this component used." This one answers "is it used correctly, and if not, here's the fix" — same tool family, an LLM added where a deterministic rule genuinely can't do the job (see Design decisions).

## Eval numbers (up front, not buried)

Measured against `llama3.2:3b` running locally via Ollama, on 22 original hand-written cases (`evals/cases/`, 24 violations found across them — see `evals/results.md` for the full breakdown, regenerated by `pnpm eval`):

- **Explanation quality: 91.7-95.8%** across repeated runs (see below — this number has real, expected variance)
- **Codemod success rate: 77.8%** (14/18 mechanical-fix-eligible violations produced a diff that type-checks)

Neither number is 100%, deliberately. Both gaps are explained below, not glossed over.

## Architecture

```
target file/diff
      │
      ▼
  AST walk (ts-morph)             ← M1.1
      │
      ▼
  rule engine (config-driven)     ← M1.2   4 rules: raw-element-should-be-component,
      │                                    hardcoded-value-should-be-token, deprecated-prop,
      │                                    hardcoded-svg-color
      ▼
  Violation[] (deterministic, no LLM yet)
      │
      ├──────────────► LLM explanation (Ollama default / Anthropic optional)   ← M1.3, M1.4
      │                 grounded in the component's real prop list
      │
      └──────────────► deterministic AST codemod, type-checked                ← M1.5
                        │
                        ├─ type-checks  → shown as a diff
                        └─ doesn't      → discarded, explanation-only
      │
      ▼
  CLI (text/json) or GitHub Action (inline PR comments)   ← M1.6
```

## Design decisions

**Rules stay deterministic; the LLM is scoped to explanation and is never the thing deciding what's wrong.** A violation is detected by an AST match against real component metadata (parsed from Project 0's actual `.tsx` source and prop types — not hand-maintained), never by asking a model "does this look wrong." The LLM's only job is to explain a violation the rule engine already found, and even that has a deterministic fallback (the rule's own message) if the LLM call fails or times out.

**Codemods are deterministic AST transforms, not LLM output, and are never auto-applied.** Once a rule fires, the fix (rename a tag, rename a prop) is already fully known — generating it with an LLM would add cost and non-determinism for no benefit. Every generated diff is type-checked against the design system's real types before being shown; if it doesn't type-check, it's discarded and the violation falls back to explanation-only. Two rule categories genuinely can't be mechanized safely (see below) and correctly do this every time, not as a bug.

**Works with zero API key or cost by default.** `LLM_PROVIDER` defaults to Ollama, running locally via `docker compose up` (`docker-compose.yml`, host port **11435** — not Ollama's default 11434, because this machine already had a native Ollama install bound to it; picking a distinct port avoids that collision for anyone else running this too). Anthropic is available as `LLM_PROVIDER=anthropic` with `ANTHROPIC_API_KEY` set, used only to record the published eval baseline — not needed for anything else.

## Real limitations found while building this (not hidden)

- **`Checkbox`/`Radio` conversions from a bare `<input>` correctly fail to type-check** when there's no label to source `label` from (an accessibility-required prop) — this is a genuine limit of static conversion, not a bug, and the tool's fallback path handles it correctly rather than emitting broken code.
- **`select` → `Select` correctly fails** for the same reason: `Select` requires an `options` prop this tool doesn't attempt to synthesize from raw `<option>` children.
- **The local model's output has real run-to-run variance.** Re-running the identical eval cases against the identical local model produced explanation-quality readings that moved by double digits between runs purely from sampling. The eval's CI gate uses a 10-point tolerance band for exactly this reason — see `evals/run-eval.ts` and `PLAN.md`'s M1.8 section for the full account, including a scorer bug of my own that this same process caught and fixed (a naive hallucination check was flagging the model for correctly mentioning native HTML attributes that aren't in a component's own declared prop list).
- **A real bug in this tool's own explanation path** (`check.ts`'s target-component extraction) went unnoticed through M1.6 and was only caught while preparing this eval — see `PLAN.md`.

## Running it locally

```bash
docker compose up -d                                    # starts Ollama on localhost:11435
docker exec <container> ollama pull llama3.2:3b         # one-time, ~2GB

pnpm install
pnpm build
node dist/cli.js check <path-to-file.tsx>               # human-readable
node dist/cli.js check <path-to-file.tsx> --format=json # machine-readable
pnpm eval                                                # regenerate evals/results.md
```
